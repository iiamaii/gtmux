설치와 업데이트

서버 배포물

OS·CPU에 맞는 압축 파일을 풉니다. frontend 폴더를 gtmux 실행 파일 옆에 유지합니다. 발행된 서버 배포물을 실행하는 데 Rust나 npm은 필요하지 않습니다.

./gtmux start --name local --port 9001 --workspace /absolute/project/folder

서버가 출력하는 최초 접속 URL을 엽니다. 토큰은 인증 정보이므로 공개하지 않습니다. 설정 파일을 유지하려면 --config /absolute/path/server.toml을 사용합니다. 기존 CLI·환경 변수의 우선순위는 유지됩니다.

데스크톱 앱

플랫폼에 맞는 패키지를 설치하고 gtmux를 엽니다. 작업 폴더와 사용하지 않는 포트를 선택하고 설정을 저장한 뒤 서버를 시작합니다. 앱은 별도 설정과 Store를 사용하며 다른 서버를 인수하거나 종료하지 않습니다.

Web, App, Web + app 중 하나를 선택합니다. 백그라운드 모드는 창을 숨겨도 트레이에 관리자를 유지합니다. 시스템 서비스 설치나 로그인 시 자동 실행을 활성화하지는 않습니다. 앱을 완전히 종료하면 앱 소유 서버와 실행 중 터미널 프로그램도 종료됩니다.

Windows에서는 gtmux-Setup-VERSION-ARCH.exe로 데스크톱 앱을 설치합니다. 설치하면 시작 메뉴 검색과 설치된 앱 목록에 gtmux가 등록되고 바탕 화면 바로가기가 만들어집니다. win-unpacked 안의 실행 파일은 압축 해제한 개발용 미리보기라 이런 항목을 등록하지 않습니다. 이후 새 설치 파일로 기존 설치를 업데이트하면 같은 앱 식별자와 사용자 프로필을 사용합니다. 제거 시에도 기본적으로 프로필을 유지하며, 업그레이드 중에는 프로필을 삭제하지 마세요. 업데이트 피드가 없는 로컬 설치 파일은 수동 업그레이드만 지원합니다.

업데이트

같은 저장소의 Releases에서 새 설치 파일이나 압축 파일을 받습니다. 앱 파일을 교체하기 전에 관리형 서버를 종료하고 데이터 폴더·설정은 유지합니다. 실행 중 프로그램은 업데이트 후 복원되지 않습니다. 롤백용 이전 패키지를 보관하되 새 Store 스키마를 이전 서버가 읽을 수 있다고 가정하지 않습니다.

소스에서 로컬 확인

빌드와 관리자 실행 명령은 기여 방법을 참고합니다. Release workflow는 다운로드 가능한 산출물을 만들지만 아직 발행하지 않은 빌드가 이미 배포된 것은 아닙니다.

Windows 네이티브 빌드

통합 브랜치는 ConPTY 기반 Windows 네이티브 실행을 대상으로 합니다. WSL이나 Python 환경이 필요하지 않습니다. ConPTY를 위해 Windows 10 1809 이상이 필요합니다. 기본 셸은 COMSPEC(cmd.exe)이며 터미널의 명시적 명령으로 PowerShell을 선택할 수 있습니다. 인증 정보에는 비공개 Windows DACL을 적용하고 서버 API 또는 프로세스별 Windows 이벤트로 종료합니다. 지원 릴리스를 선언하기 전에 Windows와 macOS CI의 실행 검증이 통과해야 합니다. 서명되지 않은 설치 파일은 OS 확인을 요구할 수 있습니다.

Windows에서는 PowerShell에서 ./gtmux.exe start --name local --port 9001 --workspace C:/Projects로 압축 해제한 서버를 시작합니다. Windows 네이티브 backend 테스트와 패키징된 앱의 시작·정지·전체 종료 검사는 로컬에서 통과했습니다. macOS 실행 검사, 서명된 배포 및 실제 공개 DNS/ACME 검증은 릴리스 검증 단계로 남아 있습니다.

릴리스 피드가 설정된 앱은 자동 확인·다운로드를 지원하며 설치는 명시적으로 확인해야 합니다. 공개 피드가 없는 로컬 패키지는 수동으로 교체합니다.
